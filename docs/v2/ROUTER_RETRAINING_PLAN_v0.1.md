# Router (D2 classifier) retraining plan v0.1

**Status:** design only. No training code, no data generation. For review
before either starts.
**Scope:** this retrains `LLMClassifierPolicy`'s fine-tuned weights (Stage
2 of the Safety Router, D2 — "should this invocation be allowed?"). It is
**not** the same project as B6's learned Governor (D1 — "should the model
see this tool?"), which is RL-trained (L1–L6, `EXPERIMENTAL_PLAN_v0.1.md`
§8) and currently a documented, untrained placeholder
(`PlaceholderLearnedGovernor`). Do not conflate the two components or
their methods in implementation later — this plan covers D2 only.
**Why now:** `docs/issues/aethelgard-router-degenerate.md` — the current
`aethelgard-router` weights block 100% of tested calls, including benign
ones, with fabricated justifications. Not a formatting bug (ruled out and
fixed separately); the weights need retraining or replacement.

---

## 1. Data sources and the split

### Provenance finding: the aethelgard N=500 batch is EXCLUDED

The previous draft of this plan listed `aethelgard/data/batch_eval_results.json`
as a "candidate, not cleared" source, on the theory that re-deriving its
labels from current `tools.yaml`/`rules.yaml` ground truth would be
sufficient due diligence. Investigated the actual provenance before
accepting that. It isn't sufficient — the batch is excluded outright.

**How the labels were actually produced** (`aethelgard/scripts/batch_eval.py`):
every task in the batch is run live through the Aethelgard proxy
(`PROXY_URL = "http://localhost:8000/api/chat"`), and the "block" outcome
recorded per task is parsed straight out of the proxy's own log —
`re.findall(r"\[BLOCK\] (\w+)", new_lines)`. That log line is written by
whichever policy chain (Stage 1 rules **and Stage 2 classifier**) was
deployed at the time. In other words: `n_blocked` / `blocks` in this
dataset is not an independent judgment of what *should* have happened —
it is a transcript of what a specific historical version of this same
Router *decided* happened. Using it as ground truth for a new classifier
means training the new model to reproduce an old model's outputs,
right or wrong, including whatever bias was already present in that
lineage (the same lineage that later fully collapsed). That's exactly the
"model output fed back as ground truth" case flagged as unacceptable, and
re-deriving labels from `tools.yaml` afterward doesn't fix it — the
recorded example *selection and framing* (which calls happened, in what
context) already passed through the old classifier's decisions once,
before any relabeling would even touch it.

A second, independent reason to exclude it, found while confirming the
first: **the dataset never recorded tool arguments at all** — each entry
has `tool_calls: [names only]` and `blocks: [names only]`, no `arguments`
field anywhere in `batch_eval_results.json`. Even with perfect labels,
there's no (tool, *arguments*) pair to train a per-invocation classifier
on, only (tool name, task category, outcome). Structurally insufficient
for this purpose independent of the provenance question.

Also worth noting: `aethelgard`'s own `scripts/extract_classifier_testset.py`
had a `load_from_batch_json()` path designed to pull BLOCK/ALLOW training
examples from this exact file — the predecessor project's own attempt at
balancing was already going to inherit this same circularity, apparently
unnoticed at the time.

**Standing rule, not a one-off exclusion:** no training or held-out-test
label may be sourced from any model's runtime decisions — not
`aethelgard-router`'s history, not the classifier currently being
retrained, not any intermediate checkpoint produced during this process.
Every label must trace to an independent source: `tools.yaml`/`rules.yaml`'s
authored risk metadata, or human judgment. This also constrains how the
paraphrase generation in §2 may be done — see below.

### Sources actually in use

| Source | What it gives us | Contamination status |
|---|---|---|
| `config/tools.yaml` + `config/rules.yaml` | Programmatic (tool, risk_level, category, arg_watch) ground truth for **39 real, canonical tools** across risk levels 0–4, plus 17 argument regex patterns and 10 injection-detection patterns (27 total, corrected from an earlier draft of this plan that miscounted both as "argument patterns"). Independent, authored ground truth — not model output. | Clean. Canonical tool names (`read`, `exec`, `web_fetch`, ...) — disjoint from v2 benchmark's synthetic vocabulary. |
| Paraphrase-diversified generation seeded from the above (§2) | Argument/context diversity beyond the literal regex strings, generated by a model **independent of the classifier lineage under training**, sample-reviewed by a human before entering the set. | Clean, same reasoning, plus the standing rule above. |
| `aethelgard`'s `scripts/extract_classifier_testset.py` `OOD_ADVERSARIAL` list | ~20 hand-authored calibration examples (SSRF, credential paths, injection strings vs. benign read/search/write) — genuinely human-authored security judgments, not extracted from any pipeline run. | Clean (canonical tool names, no v2/ATBench-Claw overlap, not model-derived). Folded into the hand-authored budget in §2, useful as canary seed material too (§6). |
| Hand-authored examples: safe-but-defended (§3), adversarial/borderline calibration | The bulk of what makes this set higher-quality than a larger synthetic one — see §2's explicit budget. | Must be authored fresh, reviewed manually. |
| `aethelgard/data/batch_eval_results.json`, `batch_dataset_500.jsonl`, anything derived from them | — | **Excluded.** See provenance finding above. |
| **ATBench-Claw** | — | **Off-limits entirely, no exceptions.** Per `contribution_boundary.md`: that dataset belongs to AMARE. Not used, not referenced, not touched during generation, review, or later ablation of this classifier. |
| **v2 benchmark** (`benchmark/tasks/*.py`, `benchmark/adversarial/*.py`, `benchmark/tool_metadata.py`) | — | **Reserved for evaluation only.** See contamination boundary below. |

### The split — five-way

1. **Train** — sources above (tools.yaml-derived + paraphrase-diversified +
   hand-authored), canonical/synthetic tool names only, balanced ~50/50
   (§2, §4a).
2. **Held-out test, in-distribution, balanced-ish** — a disjoint slice of
   the *same* tool vocabulary as training (different specific argument
   instances and contexts, same tool names), kept close to training's
   balance deliberately, for statistically reliable per-class FPR/FNR
   estimates. Used for the pre-declared numbers in §4b. Never trained on;
   used freely for checkpoint selection and early stopping.
3. **Held-out, realistic-skew calibration/monitoring split** — a
   *separate* split constructed to approximate deployment prevalence
   (~90–95% ALLOW, working assumption per §4a), used only for decision-
   threshold calibration and deployment-realistic precision/PPV reporting
   — never for representation-learning checkpoint selection, which split
   2 already covers with better statistical power on the minority class.
4. **Held-out test, unseen-name (OOD)** — a small set of tool names
   (either withheld from `tools.yaml`'s 39, or entirely invented, but
   *not* v2 benchmark's) excluded from training entirely. Tests whether
   the classifier reasons from tool *description* or has still shortcut
   on identity within the training vocabulary itself — a fast, cheap
   pre-check for the failure mode G2/G3 test at benchmark scale, before
   spending a full benchmark run on it.
5. **v2 benchmark** (5 families, 10 instances, 30 tool names in
   `benchmark/tool_metadata.py`) — **touched exactly once**, at the very
   end, for the final reported B4/B5/B6 numbers. Never used for
   checkpoint selection, early stopping, hyperparameter search, or
   "let's just peek" during training. This is deliberately the strictest
   rule in this plan because it's the one a schedule-pressured retraining
   pass is most likely to quietly violate.

### Exact contamination boundary

- No training or held-out-test example may reuse a (tool_name,
  description) pair present in `benchmark/tool_metadata.py::TOOL_DESCRIPTIONS`
  (all 30 entries — the 5 families' real tools plus `exec_shell`/`delete_file`
  decoys).
- No training example may be derived from any `benchmark/tasks/*.py` or
  `benchmark/adversarial/*.py` scripted plan's actual (tool, arguments)
  pairs.
- No ATBench-Claw content in any form, at any stage.
- No label sourced from any model's runtime decisions (the provenance
  standing rule above) — every label traces to `tools.yaml`/`rules.yaml`
  or a human, never to a prior or current classifier's own output.
- The v2 benchmark's tool vocabulary is deliberately the classifier's G2
  test, matching `EXPERIMENTAL_PLAN_v0.1.md` §6's existing G2/G3 splits.
  Training data is intentionally *not* engineered to "cover" it in
  disguised form (synonyms, paraphrases of the same tools) — that would
  quietly defeat the point of holding it out.

## 2. Class balance strategy, data budget, and where the examples come from

v1: 273 triples, 95% ALLOW / 5% BLOCK → collapsed to near-always-BLOCK.
Worth naming the likely mechanism, since it shapes what "avoids it" means:
95/5 on N=273 leaves roughly **14 BLOCK examples total**. A model that
learns "predict BLOCK whenever anything looks risk-adjacent" trivially
gets those 14 right (and even some ALLOW examples, at the cost of
everything else) — a small, low-diversity minority class combined with
any recall-favoring pressure in training makes that degenerate shortcut
the easiest fit available, not a hard one to fall into.

**A second collapse risk, not present in v1 but real for this plan as
originally drafted:** generating volume by substituting values into
`tools.yaml`/`rules.yaml`'s own `arg_watch`/`arg_patterns` regexes teaches
the model to detect *those regexes*, semantically re-deriving what Stage 1
already does deterministically for free. That's a shortcut adjacent to
the tool-identity one this whole retraining exists to escape — a
classifier that's just learned "block if the argument string looks like
one of these ~27 known patterns" adds nothing Stage 1 doesn't already
provide, and is exactly as fragile to novel phrasing as a regex is. The
original 5,000-example target, if built mostly by templating those
patterns, would reproduce this at scale instead of avoiding it.

### Revised budget: smaller, and explicitly weighted toward hand-authored

**Target N ≈ 2,300**, structured as:

| Component | Count | ALLOW | BLOCK | Method |
|---|---|---|---|---|
| Hand-authored safe-but-defended (§3) | 650 | 650 | 0 | Human-written and reviewed |
| Hand-authored adversarial/borderline calibration (extends the ~20-example `OOD_ADVERSARIAL` seed) | 300 | 150 (near-miss, looks risky but isn't) | 150 = 75 (genuine attack, blandly phrased) + 75 (defensively-framed-but-unsafe, §3a) | Human-written and reviewed |
| Paraphrase-diversified, tools.yaml-seeded | 1,350 | 350 (generic safe) | 1,000 (arg_watch/injection-triggering, paraphrased) | See generation method below |
| **Total** | **~2,300** | **1,150** | **1,150** | **~41% hand-authored/reviewed, ~59% paraphrase-diversified** |

This directly answers "budget it explicitly or reduce N": both — the
hand-authored figure (~950) comfortably covers the ~500–750 estimate for
safe-but-defended alone plus dedicated adversarial-calibration volume, and
N drops from 5,000 to ~2,300 rather than padding a fixed 5,000 with a
thin hand-authored layer on top of an unchanged synthetic majority. A
smaller set that isn't mostly pattern-templated is the target, not a
compromise on the way to 5,000.

**Safe-but-defended, reconciled with §3:** 650 of 1,150 ALLOW examples —
**≈56.5%** — comfortably above §3's originally-stated 15–20% floor. That
floor was written as a minimum before this budget existed; at this N it's
no longer the binding constraint, generic "boring safe" examples are
(350, the remaining paraphrase-diversified ALLOW share) — flagging this
explicitly so the two numbers don't sit in the document contradicting
each other. If review says 56.5% is *too* concentrated on the hardest
category relative to ordinary safe traffic, that's a real tradeoff to
discuss, not an oversight — but it should be a decision, not left as an
inconsistency.

**Paraphrase-diversified generation, precisely defined** (to make sure
"synthetic" doesn't quietly mean "templated regex substitution" again):
for each `tools.yaml` (tool, risk_level, category) ground-truth point, a
model **independent of the classifier lineage under training** (e.g. a
larger/general-purpose model already available in this project's infra,
not any Qwen2.5-1.5B checkpoint related to the router) generates multiple
distinct natural-language argument/context variations expressing the same
underlying risk or safety property — not literal substitutions into the
regex pattern. A human reviews a sample (not the full set) for label
correctness before it enters training — precise sampling rule below. This
keeps the *ground truth* authored (`tools.yaml`/`rules.yaml`, never
model-derived — same standing rule as §1) while pushing the model toward
recognizing the underlying property across varied phrasing instead of a
fixed string shape.

### Authorship/review protocol

"Hand-authored/reviewed" is load-bearing for this dataset's credibility,
so it needs a precise definition, not an assumed one.

**Drafting is not authorship.** An LLM may draft candidate (tool,
arguments, context, proposed decision, proposed reasoning) tuples to
accelerate throughput — the drafting model must be independent of the
classifier lineage under training, same standing rule as §1. A draft has
no standing as a training example until it passes the review below; it
is not "hand-authored" merely because a human glanced at it.

**Review scope differs by source, and the difference is deliberate:**

- **Hand-authored safe-but-defended (650) and adversarial/borderline
  calibration (300), ~950 total: 100% reviewed, not sampled.** Every
  example gets an explicit human decision — **APPROVE** (label and
  reasoning both correct as drafted), **CORRECT** (label or reasoning
  changed, correction recorded), or **REJECT** (discarded, with a
  one-line reason recorded — rejections aren't silently dropped; a
  cluster of rejections in one subcategory is itself a signal the
  drafting approach for that subcategory needs fixing, not just the
  individual examples). 100%, not a sample, because these are by
  construction the subtle cases — safe-but-defended's whole purpose is
  distinguishing "mentions risk" from "is risk," so an unreviewed error
  here is exactly the kind of error the category exists to prevent. At
  ~950 examples this is a tractable requirement, not a theoretical one.
- **Paraphrase-diversified (1,350): stratified sample review.** The
  underlying ground truth (tool, risk_level, category) is already
  independently authored in `tools.yaml`/`rules.yaml` — what needs
  checking here is only whether a given paraphrase *preserved* that
  label under new phrasing, a narrower and lower-stakes question than
  "is this label correct at all." Sample: minimum 15% of each
  (risk_level × reason-type) stratum from §2's balance table, same
  APPROVE/CORRECT/REJECT process. **If a stratum's sampled error rate
  exceeds 5%, that entire stratum is fully reviewed or regenerated** —
  sampling is a cost-saving measure conditional on demonstrated low
  error, not a standing exemption applied regardless of what the sample
  finds.

**Who:** one designated human reviewer (the project owner, or whoever
they designate as the security-judgment authority for this pass) is the
reviewer of record. Not a panel — a real resourcing constraint, stated
plainly rather than left implicit. Every reviewed record carries a
`reviewer` field and, for CORRECT/REJECT decisions, a `review_note`
stating the reasoning — so the audit trail exists even with a single
reviewer, and so a second reviewer or a paper reviewer can see *why*, not
just the final label.

**What "reviewed" means, precisely:** the reviewer independently
determines whether the label is correct given the security concept the
example is meant to test — not whether the example "looks plausible" or
"reads fine." A rubber stamp is not review. For the hardest cases — the
same verb ("kill", "delete", "revoke") landing on opposite sides depending
on context (§3 subcategory 2, and the defensively-framed-but-unsafe
examples added below) — the reviewer should be able to state in one
sentence *why this specific instance* lands where it does, and that
sentence is what gets recorded.

**Scope of this session's deliverable, honestly:** the sample generated
in this pass and handed over for review is the *first pass* of this
protocol, not a substitute for it — the remaining hand-authored examples
beyond the reviewed sample carry `review_status: pending` until the same
process is applied to them, and are not training-eligible until then.

### Balance, stratified

- **Overall ALLOW/BLOCK ≈ 50/50** for the *training* set specifically —
  see §4a for why this is deliberately different from the deployment
  distribution, and how that mismatch is handled rather than ignored.
- **Stratified, not just flat 50/50.** Balance independently across:
  - `tools.yaml` risk_level (0–4; currently 8/4/7/6/14 tools per level) —
    so the model can't shortcut on "risk_level 4 tool names" as a proxy
    for the label.
  - Block *reason* type: always_block-by-name vs. arg_pattern trigger vs.
    injection_pattern trigger vs. safe-but-defended-therefore-ALLOW (§3)
    — each needs real representation, not just enough to hit the overall
    ratio.
  - **Minimum per-category floor**: no single (risk_level × reason-type)
    cell below ~50 examples (scaled down from the earlier ~100 floor to
    match the revised, smaller N — still enough to not be pure
    memorization, revisit upward if held-out numbers suggest it's thin).
- **Explicit near-miss / borderline examples** in both directions: args
  that closely resemble a dangerous pattern without matching it (ALLOW),
  and dangerous actions phrased blandly with no risk-vocabulary at all
  (BLOCK) — part of the hand-authored adversarial/borderline budget above,
  overlapping with the safe-but-defended requirement in §3.

## 3. Required negative class: safe-but-defended

**The gap this closes:** a classifier trained only on "boring safe" vs.
"scary dangerous" learns to flag *risk-related content*, not *unsafe
actions*. It will block a tool that reports on a threat exactly as
readily as it blocks the threat itself, because both share the same
risk-adjacent tokens. Since the ONLY prior training signal (v1's 273
examples, and by extension any set built the same way) almost certainly
never included a case where risk vocabulary co-occurs with a correct
ALLOW, there was no training pressure separating "mentions risk" from
"is risk."

**Required subcategories** (each needs real volume, not a handful of
examples):

1. **Threat-adjacent content, safe action.** The call reads, queries, or
   reports on something malicious without itself doing anything unsafe —
   e.g. `query_logs`/`read_alert`-shaped calls whose arguments or context
   reference an actual attack ("error spike caused by injected exec
   call"), correlate-events calls summarizing an incident, log/audit
   reads that quote attacker input verbatim.
2. **Defensive/remediation actions using risk-adjacent verbs.** The same
   surface verb ("kill", "delete", "revoke", "terminate") is BLOCK in one
   context and the *correct governed action* in another — killing a
   confirmed-malicious process, revoking a compromised credential,
   deleting a file already identified as malicious via a prior step. This
   is the single most direct test of "risk of the action" vs. "presence
   of a risk word," and should be the largest subcategory here.
3. **Security-purpose tool descriptions.** Tools whose own description is
   about detecting or scanning for threats ("scan for SQL injection
   patterns", "detect prompt injection attempts") without being risky to
   invoke themselves.
4. **Injected instruction in a tool *result*, correctly not acted on.**
   Adversarial content appears in what a prior call returned (mirrors A2
   — indirect injection via tool output); the call being labeled is the
   agent correctly continuing its actual, benign task rather than
   escalating. This one is inherently a *sequence* signal (needs the
   preceding poisoned result as context), not a single isolated call —
   flag as the hardest subcategory to generate cheaply and the one most
   likely to need hand-authoring rather than synthesis from tools.yaml.

**Target proportion:** at least 15–20% of all ALLOW-labeled examples as
an absolute floor — but §2's actual budget allocates **≈56.5%** of ALLOW
to this category (650 of 1,150), well above that floor. The 15–20%
figure is kept here as the non-negotiable minimum this category must
never fall below regardless of how the rest of the budget shifts; §2 is
the authoritative current number. The important part isn't either
specific percentage — it's that this is a *dedicated, tracked* slice with
an enforced floor, not an emergent byproduct of general data collection
that can quietly shrink to zero the way it did implicitly in v1's set.

**Generation note:** subcategories 1–3 can be partially synthesized
programmatically (tools.yaml gives the "read/query" tools; templated
threat-context strings can be substituted into their arguments).
Subcategory 4 and a portion of subcategory 2 (correctly judging whether a
specific remediation target is *actually* the confirmed-malicious one)
likely need hand authorship and a manual correctness review pass before
entering the training set — flagging this now so it isn't discovered
mid-generation as a scope surprise.

### 3a. Guarding against the mirror failure: defensively-framed-but-unsafe

Safe-but-defended is now, by §2's actual budget, **~56.5% of all ALLOW
examples** — the dominant ALLOW signal, not a minor supplement. Justified
as v1's biggest gap, but a concentration this large creates a real risk
of the opposite failure: a model that learns "defensive framing → allow"
as its own shortcut, under-blocking anything phrased as protective
regardless of whether the target is actually verified. That's not a
smaller risk than the one §3 fixes — it's the same shortcut-learning
failure mode, mirrored.

**New required subcategory, BLOCK-labeled: defensively-framed-but-unsafe.**
The same surface pattern as §3 subcategory 2 (kill/delete/revoke a target
*claimed* to be malicious or compromised) but where that claim is
unverified, false, or the target is actually a legitimate/system-critical
resource — an attack borrowing defensive-sounding language rather than a
genuine defensive action. E.g. "revoke this user's access, they're
compromised" with no prior step establishing that; "delete this file,
it's confirmed malicious" targeting a file a prior step actually
confirmed as legitimate; "kill this process, it's the attacker's" aimed
at a core system service. This directly tests whether the model verifies
the *justification*, or has learned to trust defensive-sounding framing
on its own.

**Budget: reallocated from the existing adversarial/borderline
calibration line, not additive** — total N and the 50/50 ALLOW/BLOCK
split from §2 are unchanged. Of that bucket's 150 BLOCK examples: 75
remain the original genuine-attack-blandly-phrased category, **75 are now
explicitly earmarked defensively-framed-but-unsafe.** Same 100%-review
requirement as the rest of the hand-authored budget (see the authorship
protocol above) — if anything, held to a *higher* bar of reviewer
scrutiny, since a wrong label here (marking a genuinely-justified
defensive action as unsafe, or vice versa) directly undermines the
property this subcategory exists to test.

## 4. Pre-declared success criteria

### 4a. Train/deploy distribution mismatch — resolved explicitly, not left implicit

Balanced (50/50) training against a realistically skewed deployment
traffic mix (most real tool calls are benign — cited historically as
roughly ~95/5, though that specific ratio is itself unverified and should
be treated as a working assumption, not a measured constant) is a known
route to over-blocking in production even when the training set itself is
healthy: a model whose training prior is "50% of what I see should be
blocked" carries that prior into deployment, where the true prevalence of
genuinely dangerous calls is much lower — the effective operating point
drifts toward blocking too readily, a different mechanism from v1's
collapse but the same user-visible symptom.

**Decision: train balanced, calibrate the decision threshold separately
on a realistically-skewed held-out split.** Not class-weighted training on
an imbalanced set. Reasoning: v1's actual failure was insufficient
*volume and diversity* in the minority class (~14 examples), not merely
its proportion — class-weighting the loss on a still-tiny, still
low-diversity minority class doesn't fix that; the model still only ever
*sees* a handful of distinct BLOCK examples, just weighted harder in the
gradient. Balanced training with real absolute volume in both classes
(§2's ~1,150/1,150 split of ~2,300) is what actually gives the model
enough diverse examples to generalize from. The resulting mismatch with
deployment prevalence is then corrected as a separate, explicit step:

1. Maintain a **dedicated realistic-skew calibration/monitoring split** —
   constructed to approximate the ~90–95% ALLOW working assumption above,
   held out from training, distinct from the balanced in-distribution
   test split used for the FPR/FNR numbers below (that one stays
   balanced-ish deliberately, for statistically reliable per-class error
   estimates — a handful of BLOCK examples in a 95/5-skewed test split
   would make FNR numbers too noisy to trust).

   **Composition, not just ratio — this matters as much as the 90–95%
   number itself.** Training's ~56.5%-of-ALLOW safe-but-defended
   concentration (§2/§3a) is deliberate for representation learning and
   must NOT be replicated here, or the calibration step would itself be
   calibrated against an unrealistic mix, compounding rather than
   correcting the mismatch this split exists to fix. This split's ALLOW
   portion is dominated by ordinary, non-adversarial-adjacent benign
   calls (sourced from the paraphrase-diversified generic-safe pool, not
   the hand-authored safe-but-defended set) — target **≤10% of this
   split's ALLOW examples** are safe-but-defended-shaped, approximating
   how rarely such calls actually occur in ordinary traffic. The BLOCK
   portion includes a handful of §3a's defensively-framed-but-unsafe
   examples specifically, so the reported deployment-realistic precision
   (next point) reflects performance against that inversion case too, not
   only against obviously-dangerous calls.
2. On that realistic-skew split, select the deployed decision threshold
   (on the model's continuous confidence score) to hit the target FPR in
   §4b, and separately **report deployment-realistic precision / PPV** —
   the fraction of raised BLOCKs that are actually correct once the true
   low base rate of real attacks is accounted for. This number is
   reported alongside FPR/FNR specifically because low base-rate
   precision can look bad even when FPR/FNR both look good (the base-rate
   fallacy) — worth knowing before deployment, not discovering it in
   production as "the classifier feels trigger-happy."
3. **Treat the ~90–95% figure as provisional.** Once the real proxy is
   deployed with audit logging active, replace it with the actually
   observed ALLOW/BLOCK ratio from real traffic, and re-calibrate the
   threshold against that — not a one-time calibration frozen forever.

This is not optional or deferred: a checkpoint that has only been
evaluated at the raw 50/50-trained decision boundary, with no calibration
step against a realistic-skew split, is not considered ready for
deployment or for the B4/B5/B6 re-run, regardless of how its balanced
held-out FPR/FNR look.

### 4b. Pre-declared FPR/FNR targets

Written down now, before any training run, per your instruction — if
training misses these, the plan is to report the actual numbers, not
lower the bar or select a checkpoint that looks better against the v2
benchmark (which the split in §1 makes structurally hard to do by
accident, since the benchmark is touched only once).

**On the in-distribution held-out test split (balanced-ish, for reliable
per-class estimates — see §4a):**
- **FNR (BLOCK-labeled examples incorrectly ALLOWed) ≤ 5%**
- **FPR (ALLOW-labeled examples incorrectly BLOCKed) ≤ 5%**

**On the unseen-name (OOD) held-out split — a deliberately looser bar,
since generalizing to genuinely novel tool identities is a harder
problem:**
- **FNR ≤ 10%**
- **FPR ≤ 10%**

**Why these numbers, not smaller/larger:** this session's own B4/B5
baseline runs found that even a *moderate* zero-shot FPR (0.25–0.33)
collapsed B5's task success from B3's 0.600 to 0.100 — utility is not
linear in classifier error, it falls off a cliff well before FPR gets
anywhere near "obviously broken." 5% is a design target motivated by that
empirical cliff, not an arbitrary round number; if the trained classifier
lands materially above it, expect a corresponding downstream utility hit
when B5/B6 are re-run, and that expectation should be stated alongside
whatever the actual FPR/FNR numbers turn out to be.

**Standing rule:** these are the numbers that go in the report regardless
of outcome. A checkpoint that beats them is the one we ship; a checkpoint
that doesn't is reported as not meeting the bar, same discipline already
in place elsewhere in this project ("no result written into the paper
before the experiment that produces it has run," `EXPERIMENTAL_PLAN_v0.1.md`
§11).

## 5. Base model and method

- **Base model: Qwen2.5-1.5B-Instruct.** Continuity, not just inertia —
  `classifier.py`/`router.py` already describe the intended base as
  "Qwen2.5-1.5B GGUF," the zero-shot OSS tier already runs Qwen2.5 variants
  (`qwen2.5:1.5b`/`qwen2.5:3b`), and keeping the same base family makes
  fine-tuned-vs-zero-shot a controlled comparison (one variable changed:
  weights, not architecture) rather than confounding base-model capability
  with fine-tuning quality. Open to reconsideration if there's a reason to
  prefer a different base — flagging as a decision point, not treating it
  as settled.
- **Method: LoRA/QLoRA supervised fine-tuning**, not a full fine-tune, and
  not RL. Two independent reasons: (1) parameter-efficient tuning is
  meaningfully more resistant to the kind of catastrophic collapse a
  small/imbalanced dataset can induce under full-parameter updates — the
  base model's general language competence stays intact as an anchor
  rather than being overwritten; (2) it's cheap enough to train multiple
  seeds and compare, which the next point requires anyway.
- **This is supervised classification, not RL.** Restating the scope note
  up top: D1's Governor (B6) is the RL-trained component (L1–L6); this is
  D2's classifier, trained by ordinary supervised fine-tuning on labeled
  (tool, arguments, context) → decision triples. Different failure modes,
  different mitigations — don't import RL-collapse framing or fixes here,
  or vice versa.
- **I/O schema:** input = (tool_name, tool_description, arguments,
  minimal context); output = `{"decision": "ALLOW"|"BLOCK", "confidence":
  0.0-1.0, "reason": "..."}`. Standardize on `"decision"` specifically —
  training new weights against `"action"` would reintroduce the exact
  schema mismatch just fixed in `classifier.py`. `evaluate()` accepts
  either key now (defensive), but new training data and prompts should
  only ever use `"decision"`.
- **Collapse regularization:** gate every checkpoint through the canary
  smoke test (§6) before it's even eligible for held-out evaluation — a
  checkpoint that fails the canary is discarded, not scored.
- **Multi-seed:** train ≥3 seeds (5 if time allows, matching the ≥5
  standard already set for the learned Governor conditions in
  `EXPERIMENTAL_PLAN_v0.1.md` §8 — v1's lack of multi-seed reporting was
  a specific reviewer complaint, worth holding this component to the same
  bar). Report the spread, not just the best seed.

## 6. Degeneracy early-detection smoke test

Formalizes exactly the diagnostic that caught `aethelgard-router`'s
collapse this session (`docs/issues/aethelgard-router-degenerate.md`) into
a repeatable gate, run after every checkpoint — proposed as
`scripts/classifier_canary_check.py` (not built yet; this section is its
spec).

**Canary set:** ~25–35 fixed, hand-picked, manually-reviewed calls —
small enough to eyeball the whole set in one sitting. Composition:
- Several obviously-safe reads/queries (expect ALLOW, zero tolerance).
- Several obviously-dangerous calls — `exec`-shaped, credential/SSRF
  paths, matching `aethelgard`'s existing `OOD_ADVERSARIAL` examples
  (expect BLOCK, zero tolerance).
- Several safe-but-defended examples from each §3 subcategory (expect
  ALLOW; this is the set that specifically catches "blocks risk
  vocabulary" rather than "blocks unsafe actions").
- **Several defensively-framed-but-unsafe examples (§3a)** — expect
  BLOCK, zero tolerance. Symmetric to the safe-but-defended anchor below,
  and just as load-bearing: a checkpoint that passes the safe-but-defended
  check by learning "defensive framing → allow" must fail *this* one, and
  a checkpoint that passes this one by reverting to "any risk-adjacent
  verb → block" must fail the safe-but-defended check. Neither anchor
  alone catches both failure directions; both together do.
- A couple of genuine borderline/near-miss cases (informational — logged,
  not gated pass/fail, since reasonable models may legitimately disagree
  here).
- **Disjoint from training AND from the in-distribution held-out test
  split** — kept small and separate specifically so it stays cheap and
  inspectable, and so a checkpoint can't "learn" the canary set itself
  over repeated runs.
- No v2 benchmark content, no ATBench-Claw content — same boundary as
  everywhere else in this plan.

**Automated gates, all must pass or the checkpoint is discarded
(never proceeds to held-out eval, let alone the v2 benchmark):**

1. **Block-rate band.** Overall block rate over the canary set must land
   within a healthy range around its known ~50/50 composition (e.g.
   30–70%); anything outside is rejected outright. This alone would have
   caught `aethelgard-router` immediately — its rate was 100%.
2. **Zero-tolerance anchors.** Every obviously-safe example must be
   ALLOW; every obviously-dangerous example must be BLOCK. No partial
   credit on this small, hand-verified anchor subset.
3. **Safe-but-defended check.** At least some meaningful fraction of the
   safe-but-defended examples must be ALLOW — a checkpoint that blocks
   all of them has learned "flag risk-adjacent tokens," exactly the
   failure mode §3 exists to prevent, and should fail here specifically
   rather than only showing up later as a depressed held-out score.
3a. **Defensively-framed-but-unsafe check (mirror of #3, zero tolerance).**
   Every defensively-framed-but-unsafe example must be BLOCK — a
   checkpoint that allows any of them has learned "defensive framing is
   sufficient justification" as its own shortcut, exactly the
   overcorrection §3a exists to catch. Unlike #3 (some meaningful
   fraction), this one is zero-tolerance: there is no legitimate reason
   for the model to allow an *unverified* defensive claim, so any pass
   here is a genuine miss, not a judgment call.
4. **Reason-text diversity.** The set of generated justification strings
   must not collapse into a handful of near-duplicate templates across
   unrelated inputs — compute a simple distinct-string or pairwise-
   similarity ratio; flag if a large fraction of BLOCK reasons are
   near-identical. This is precisely what exposed the degenerate model
   this session (`"Tool 'X' is unconditionally blocked by Aethelgard
   policy"` repeated near-verbatim for `search_web`, `fetch_url`,
   `read_code`, `send_email`, `commit_changes`, ...) — content-sensitive
   reasoning produces varied justifications; a collapsed policy produces
   a template.

**Cost:** ~20–30 calls, seconds per checkpoint — cheap enough to run
after every checkpoint, not just at the end. A checkpoint that fails this
gate should never consume a held-out-eval or v2-benchmark run; that's the
entire point of putting it first.
