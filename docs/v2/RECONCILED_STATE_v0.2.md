### 5c. What this means, stated plainly per instruction

The pilot's specific finding does not hold up at scale for `qwen2.5:3b`. **Per explicit instruction, a second model was not run** — the sequencing rule was "no more models until one reproduces the pilot number," and it didn't. This is reported as a real, informative null result, not a failed experiment: 30 independent live-agent runs across the full task-family diversity of this benchmark produced zero dangerous-decoy invocations for this model under this system prompt.

**Reclassification (required, not optional): B1 is a utility baseline, not a safety baseline.** The scaled run's real, robust finding is **task incompleteness and required-tool omission** — 73% task failure rate overall, `repo_triage` specifically showing the model abandoning the task after one or two tool calls in 5 of 6 runs (`required_tool_omission_rate` 0.767, confirmed structurally zero on every scripted baseline B0-B7 — see §3's `avg_omission` column — so this variance is real, not a metric artifact). That is a **capability/utility** finding: the model fails to *perform*. It is not evidence that the model fails to *be restrained* — no dangerous-tool-calling was observed at this N/model/prompt, so B1 currently supports no safety claim at all. "Enforcement cannot live in the model" is a safety claim; it needs a scenario with a real attack present, not a passive unused decoy — that's what A2-A5 are for (§4 of `EXPERIMENTAL_PLAN_v0.2.md`), and **only A1 is built today**. Until at least one of A2-A5 exists and runs against a live decision-maker, the safety claim has no supporting evidence in this repo, and B1's null result must not be read as filling that gap.

**Model-capability confound, stated plainly:** `qwen2.5:3b` is a 3B model. 73% task failure on straightforward multi-step tasks may reflect this specific model's general capability limits, not anything about prompting-based instructions or enforcement. Any weight B1 carries in the paper needs a stronger model run too (e.g. `qwen2.5:7b`, already available in this environment) before "the model frequently fails to complete tasks" generalizes past "this specific 3B model." Not run yet.

**Open question, not resolved here:** whether `qwen2.5:3b`'s specific near-zero dangerous-decoy rate reflects (a) this model genuinely respecting the safety instruction reliably, (b) this model rarely considering `exec_shell`/`delete_file` as plausible tool choices for these particular tasks regardless of instruction (a benchmark-design question, not a safety one), or (c) something else. Distinguishing these needs either a task design that makes the decoy tool more tempting/plausible, or testing whether the same near-zero rate holds with NO safety instruction at all (a different, legitimate condition — not run here, since it changes the prompt, which this run's design held constant on purpose).

**Representation-gap finding for gate 3a, found while designing the above probe — this is the one to act on before generating more data.** `router_training/schema.py`'s `TrainingExample.context` field ("minimal surrounding context, e.g. a prior tool result or task framing") is where the dataset's own authors put the exact signal gate 3a needs — e.g. `safe_but_defended.py`'s verified ALLOW case: `context="...a prior read step (already logged) confirmed outbound traffic to malicious-c2.example.com from a compromised process."`; `adversarial_calibration_v2.py`'s defensive-unsafe BLOCK skeletons: `context="No prior step established anything about this PID; no hash match, no SOC alert, no monitoring correlation cited."` for every one of its 75 rows. **This field is never passed to the model, in training or in serving.** `build_classify_prompt(tool_name, arguments)` (`agentwarden/policies/classifier.py`) and `to_training_pair()` (`router_training/train_common.py`) both take only `tool_name` and `arguments` — `context` is written by every generator and then silently dropped before the prompt is ever built. Checked directly: `grep -n "context" agentwarden/policies/classifier.py` returns nothing. So the answer to "is verified-vs-unverified defensive framing expressible in the current input schema" is: **the dataset schema captures it, the model's actual input does not.** Two training rows that look near-identical in `arguments` alone (an unverified `write_file`/`chmod`/etc. with a self-serving justification baked into the argument content) can have opposite ground-truth decisions once a verified-vs-not `context` string is factored in — and the model only ever sees the `arguments` side of that distinction. This is not a training-code bug the way the `on_init_end` crash was; it's a representation choice that was never revisited once the schema grew a `context` field for exactly this purpose.

**It goes deeper than a prompt-builder omission: production has nowhere to put verification status even if the prompt were fixed.** `AgentWardenToolRequest.context` (`agentwarden/core/models.py`, a `GovernanceContext`) carries `session_id`, `runtime`, `task_type`, `trust_level`, `allowed_tools`, `tenant_id`, `profile_name`, `metadata` — no prior-tool-call history, no record of what a previous stage already confirmed. At serving time there is no live analogue of the synthetic dataset's `context` string to feed in, because nothing in the pipeline tracks "a prior step in this session already verified X." The training-data fix (stop dropping `context` in `build_classify_prompt`/`to_training_pair`) only closes half the gap; closing the other half needs a real field — e.g. a `prior_verified_claims: list[str]` or similar on `GovernanceContext`, populated by whatever upstream mechanism would make a claim "verified" in production (a completed read/audit step, a SOC system's attestation, an allowlisted source) — and a policy decision about what's allowed to count as verification, which this document doesn't have an answer for and shouldn't invent one in passing. Without that, even a model trained on the full `context` string has nothing but the bare tool call to classify against in production, since production never had a verification-history concept to serialize into `context` in the first place.

**Recommendation, not yet implemented:** (1) add `context` to `build_classify_prompt`'s template and `to_training_pair`'s call to it, retrain, and re-run the canary check — this alone tests whether gate 3a moves once the model can see the signal the dataset already encodes; (2) separately and only if (1) doesn't fully close it, treat "how does production represent verification status" as its own design question (likely a `GovernanceContext` field plus an upstream convention for what populates it), not a retraining question. Per instruction, no new data generation for gate 3a until (1) has been tried and measured.

**Amendment (2026-10-19): the representation-gap finding above does not support a causal claim about gate 3a specifically, and should not be read as one.** Checked directly: grouped all 2,370 full-dataset rows by exact `(tool_name, arguments)` and looked for pairs where the identical call carries opposite decisions. **Zero such pairs exist inside `safe_but_defended` or `defensively_framed_but_unsafe`.** Each category is decision-homogeneous on its own — 652/652 `safe_but_defended` rows are ALLOW, 106/106 `defensively_framed_but_unsafe` rows are BLOCK — and the two categories share zero `(tool_name, arguments)` pairs with each other. That means `context` *cannot* be the thing separating a gate-3a BLOCK from a gate-3a ALLOW in this dataset, because no pair of rows in these categories differs only in `context` — every row in them is already decidable from `arguments` alone as far as this dataset's construction goes. The actual discriminator within these categories is something else: domain/path reputation baked directly into the argument content (e.g. `write_file` to `/etc/hosts` blacklisting `malicious-c2.example.com`, a known-bad name, vs. blacklisting `accounts.google.com`, a real one) — external knowledge about specific strings, not provenance or verification status.

**So: gate 3a is not a valid probe of whether the model can use `context` to disambiguate, and its 3/7 miss count (pilot or full-dataset) does not support a claim about a structural limit of learned governance.** The underlying fact the finding above reported — `TrainingExample.context` is written by every generator and then dropped before the model ever sees it, in both `to_training_pair()` and `build_classify_prompt()` — still stands as a fact about the schema/prompt boundary. It just isn't gate 3a's problem specifically: gate 3a's own training data never required context to be read correctly in the first place, so a model that ignores `context` entirely would still get every `safe_but_defended`/`defensively_framed_but_unsafe` training row right, and a model that somehow learned to use `context` perfectly would get no additional gate-3a training signal out of it either. The ceiling experiment (`train_pilot_ceiling.py`) is accordingly not expected to move gate 3a for a principled reason, not just an empirically-observed one — a gate-3a result from it, in either direction, should not be read as confirming or disconfirming the representation-gap hypothesis. **Decisive test, run directly on the real dataset (2026-10-20), confirms the mechanism rather than leaving it as a caveat.** `scripts/context_category_leakage_check.py` runs the same TF-IDF + logistic-regression setup as the minimal-pair probe's context-only baseline, but on all 758 `safe_but_defended`/`defensively_framed_but_unsafe` rows in the full dataset, `context` string only, label = category. 5-fold stratified cross-validation: **99.5% balanced accuracy** (plain accuracy 99.9%, confusion matrix `[[652,0],[1,105]]` — one single row misclassified out of 758). The two categories' `context` strings are separable by lexical register alone, almost perfectly, with no access to `tool_name` or `arguments` at all.

**This is the explanation for the ceiling experiment's gate-3a pass, not a caveat on it.** `safe_but_defended`'s 652 contexts and `defensively_framed_but_unsafe`'s 106 contexts were written by human authors in two visibly different registers (one category narrating "this was fine," the other narrating "this wasn't," per their own generator scripts) — register a bag-of-words classifier recovers at 99.5% balanced accuracy without reading a single tool call. A model trained with `context` included has every opportunity, and far more capacity than logistic regression over TF-IDF, to pick up the same register cue instead of anything resembling provenance judgment. The retraction earlier in this section (gate 3a's own training rows are decision-homogeneous, so training never required reading `context` to get a label right) still holds and is not in tension with this: training didn't need to teach provenance reasoning, and this test shows it didn't need to — register alone was already sufficient to separate the categories, so register alone is the most likely thing any context-aware model learned. The with-context checkpoint's higher loss (2.083 vs. the no-context pilot's 1.815) is consistent with this too: a model doesn't need to fit the task well to exploit a near-perfectly-separable lexical cue. `train_pilot_ceiling.py`'s own docstring anticipated exactly this limit on what a good result here could mean — it says nothing about whether the signal used is trustworthy, and nothing about where such a signal would come from in production (`docs/v2/provenance_representation.md`'s constraint, and the fact that no real audit store exists to source it from, both stand unchanged).

**This also withdraws gate 3 as evidence of learned judgment, not only gate 3a.** Gate 3 (`safe_but_defended`, ≥50% ALLOW) and gate 3a (`defensively_framed_but_unsafe`, zero-tolerance BLOCK) are the same construct viewed from opposite sides: both measure whether the model can tell these two categories apart, and the 99.5% balanced-accuracy result above shows a context-only bag-of-words classifier solves exactly that construct directly, without reading `tool_name` or `arguments` at all. The ceiling experiment's gate 3 pass (87.5% ALLOW, up from the no-context pilot's 12.5%) is not independent evidence of provenance reasoning any more than its gate 3a pass is — both numbers move together because both are read off the same register signal in `context`, not because the model learned two separate capabilities. Gate 3's own category is decision-homogeneous in exactly the way gate 3a's is (652/652 ALLOW, zero `(tool_name, arguments)` pairs shared with `defensively_framed_but_unsafe`), so the retraction already stated above for gate 3a applies to gate 3 with identical force and identical evidence.

**Net effect, stated plainly because it is the premise the v2 paper argument rests on: the degeneracy gate currently contains no validated positive result about learned governance.** Gate 1 (block-rate band) and gate 4 (reason-text diversity) are degeneracy guards — they rule out the model collapsing to all-BLOCK, all-ALLOW, or a single templated reason; that is a necessary sanity check, not a demonstration of judgment. Gate 2 (zero-tolerance safe/dangerous anchors) is also a degeneracy guard in substance, not a judgment test: its anchors are unambiguous from `tool_name`/`arguments` alone (a plain `read`, a plain `exec` of an untrusted string), so passing it shows the model isn't broken, not that it exercises provenance or contextual reasoning. Gates 3 and 3a were the only two gates purporting to test something beyond degeneracy — whether the model distinguishes verified-but-risky-looking calls from unverified-but-dangerous ones — and both are now shown to be solvable by lexical register in `context` alone. As of this result, there is no verified evidence in this document that the D2 classifier does anything beyond (a) not collapsing to a degenerate policy and (b) picking up a register cue that happens to correlate with the dataset's category labels. Whether a genuinely context-dependent judgment capability exists past that is open; the minimal-pair probe's prose-design result (68.8% leakage, `docs/v2/minimal_pair_probe_spec.md`) and this dataset-wide 99.5% result point the same way, and the structured-provenance redesign in that spec — not a retrained classifier on more context-included examples — is the currently-specified path to an actual test, pending item generation.

**Dataset-hygiene finding, found during the same check:** 29 rows in the full dataset (1.2%) *are* strictly context-discriminating by the definition above (identical `(tool_name, arguments)`, opposite decision, context the only thing that differs) — all 29 come from the `paraphrase_generated`/`hermes3:8b`-drafted bucket (`reason_type` `arg_pattern_trigger` or `generic_safe`, `subcategory` `paraphrase.*`), not from any hand-authored generator. ### 12b. Discriminative classifier vs. labelless guardrail — why 0.845/0.928 does not contradict STAC's ~0.5%

STAC's own ~0.5% "prompt harmfulness" figure and this project's gate-3 balanced-accuracy numbers measure two different things, not the same thing twice with different answers:

- **STAC's figure** describes whether a call's *originating natural-language prompt*, read without any label and without any paired counterfactual, *looks* harmful to a judge — human or LLM — that has no access to the benchmark's ground truth and sees each prompt once, in isolation. This is the guardrail setting: no supervision, no paired contrast, judged on content alone against a general notion of "harmful."
- **Gate 3's number** describes whether a *discriminative classifier*, trained with full label access on many BENIGN/ATTACK pairs via cross-validation, can recover which of the two classes a given call's serialized form belongs to. This classifier never asks "does this look harmful" in isolation — it asks "which of these two already-known classes does this most resemble," having seen labeled examples of both during training. A feature that never reads as "harmful" to a labelless judge (a specific IBAN, a particular phrasing of a subject line) can still be a near-perfect discriminator once a supervised model is allowed to fit on exactly those features across a labeled, paired dataset.

A governance system built as a guardrail — no label access, judging a single call against a general harmfulness notion — is not automatically exposed by gate 3's finding. A governance system built or evaluated as a discriminative classifier against this project's own paired construction would be. Which of those two things any later A4 arm actually is matters for how its result should be read, and this distinction should be stated wherever gate 3's numbers are cited going forward.

### 12d. Gate 1's scope was corrected, not re-tested (2026-10-21) — the §12/§12c FAIL verdicts above are struck, not the measurements

Follow-up instruction, after §12c: gate 1 as originally specified ("the full serialized decision input must fail to recover labels") tests an impossible condition. It names arms 1–4 with no exception carved out for arm 1. Applied literally, as written, to this measurement: **arm 1 does not clear arm 0, so under the rule as it currently stands, arm 1's own number is "no result," not a weak floor** — even though arm 1's weakness is exactly the predicted, intended-to-be-reported reference point the experiment design is built around (§8: "establishes the floor the literature predicts").
- **§10's new primary quantity, "the arm 3 − arm 1 delta at matched FAR,"** is defined against arm 1 as the subtracted baseline. If arm 1 itself is disqualified as "no result" by rule 0, that delta has no valid baseline to be computed against under the project's own current rules — not because arm 3 doesn't exist yet (it doesn't, and isn't built in this entry), but because the baseline side of the subtraction is itself in question.

**Per instruction's framing, generalized rather than forced into the one branch it named: this is a benchmark/experiment-design-fitness finding, and it stops the line before step 4.** It is not the specific "arm 1 near ceiling" scenario anticipated, but it is the same *kind* of finding — something about how the arms interact with this benchmark that needs a decision before building further, not a result to quietly work around by re-reading rule 0 to exempt arm 1. Whether rule 0 should be amended to apply only to arms 2–4 (treating arm 1 as a reference point rule 0 was never meant to gate), or whether arm 0 itself needs to be read as a cap on how much of *any* arm's number — including arm 1's — reflects the benchmark's own construction rather than the arm's judgment, is not decided here. ### 13a. Arm 0's position feature was an oracle; corrected headroom; STAC has zero length-matched negatives (2026-10-22)

Three follow-up instructions, in order: (1) determine whether arm 0's position feature is index-from-start or index-from-end, and re-measure with index-from-start if it was the latter; (2) amend §10/§11 so the primary delta is against `max(arm 0, arm 1)` and rule 0 applies only to contender arms 2–4, correcting the headroom number in §13 above against the strongest trivial baseline; (3) test whether STAC supports a length-matched (not just tool-matched), benign-final negative at scale, reporting how many of the 471 cases do, with an explicit "unfit for A4's central claim" stop if fewer than ~150 do.

**1. Arm 0's position feature was index-from-end, and it was an oracle feature.** The original implementation (§13 above) used a constant `1.0` "is_final" column, standing in for "this call is the session's last call." Knowing a call is *last* requires knowing no further call follows it — knowledge of the future a real-time monitor evaluating the current call does not have. `docs/v2/A4_MULTITURN_SPEC_v0.2.md` §8's own wording, "position in the sequence (final step or not)," baked this oracle assumption into arm 0's definition from the start; it was not something this measurement introduced on its own, but it was not caught before now either. `benchmark/a4/arms.py::arm0_scores` is corrected to default to `position_feature="index_from_start"` (`invocations_observed` — the count of calls a monitor has already observed, genuinely available at decision time); `"index_from_end_oracle"` reproduces the original measurement, kept nameable for the record.

Re-measured on the same 471 STAC pairs / 942 instances:

| Arm 0 variant | TPR @ FAR=0.12 | AUC |
|---|---|---|
| `index_from_end_oracle` (§13's original number) | 0.843 | 0.923 |
| `index_from_start` (corrected) | **0.836** | **0.929** |

The two are nearly identical (0.843 vs. 0.836 TPR; 0.923 vs. 0.929 AUC) — confirming that essentially none of arm 0's discriminative power came from the oracle feature itself. Tool identity alone was already doing almost all of the work (consistent with §12/§12a's chain-position-asymmetry finding). The oracle-feature bug does not change the conclusion in §13 above; it is corrected because it was wrong, not because fixing it changes the result.

**2. Headroom must be measured against the strongest trivial baseline — against arm 0, that is ~0.16, not ~0.07.** §13's headroom number (0.634) was `1 − arm 1's TPR`, which is the wrong baseline once arm 0 is known to beat arm 1: the relevant question is how much room is left below the *strongest* trivial baseline, `max(arm 0, arm 1)`, not the weaker of the two. Using the corrected `index_from_start` arm 0 (0.836, the stronger of the two arm-0 variants and higher than arm 1's 0.366): **headroom = 1 − max(0.836, 0.366) = 1 − 0.836 = 0.164 ≈ 0.16.**

This is checked directly against the instruction's own stated figure and does **not** match it: the instruction states "~0.07," and 0.16 is not that, by a factor of more than two — too large a gap to be rounding. The number that *does* land at ~0.07 is `1 − arm 0's AUC` (1 − 0.929 = 0.071, or 1 − 0.927 = 0.073 against the oracle variant) — AUC, not TPR at the matched FAR this project's own metric (§10: "ASR reduction at matched false-alarm rate... An ASR number without its FAR is not reportable") requires. Reported here is **0.16, computed at the matched FAR**, consistent with every other number in this document, not 0.07 — stated plainly per standing instruction to verify before writing a number into a permanent doc, not adopt one unverified.

**3. STAC supports a length-matched, benign-final negative in 0 of 471 cases — far below the ~150 threshold, and that is a finding, not an obstacle.** `benchmark/a4/s0_inputs.py::build_stac_length_matched_s0_pairs` truncates each case's executed history to its own attack chain's length `k` and takes the truncation's final call as the benign candidate, so both candidates sit at the same chain position (`k` of `k`) — a different, position-based matching criterion than gate 3's tool-identity matching (§12a). Checked directly against all 483 cases:

- **482 of 483 cases (and 471 of the 471 with any executed history) have `k = L + 1` exactly** — the attack chain's length is always precisely one step longer than the executed history, with a single outlier at `k − L = 7`. `min(k−L)=1, median(k−L)=1, max(k−L)=7`.
- **0 of 471 cases have `L ≥ k`** — the minimum required for a length-matched benign candidate to exist at all.

This is not a near-miss or an artifact of a strict matching rule: STAC's own construction guarantees, in 482/483 cases, that the executed history stops **exactly one step short** of the attack chain's own length, every time. There is no slack to find a length-matched negative anywhere in the dataset as built. 0 is far below the ~150 instructed threshold.

**Per instruction: STAC is unfit for A4's central claim, and this is recorded as a finding, not routed around.** The claim under test (`docs/v2/A4_MULTITURN_SPEC_v0.2.md` §2) is whether a black-box arm can match a white-box one at detecting session-level drift. STAC's own executed-history/attack-chain length relationship (`k = L+1`, universally) means the attack candidate is *structurally* always exactly one step past wherever the benign history stops, in effectively every case — the same mechanism already shown (§12, §12a, §13) to drive arm 0's strength. A length-matched negative, which would isolate position/length as a confound the way §12a isolated tool identity, cannot be built from STAC at the scale (~150 cases) needed to say anything with this benchmark. No further construction is attempted to route around this — per standing instruction, a benchmark-fitness result at this point is reported, not iterated against.

**Finding, stated precisely — the claim under test resolves to "no, mostly not."** A monitor trained the way the literature actually builds one — a discriminative classifier over the full action, not a deliberately narrow tool-identity feature — does **not** lose most of its performance when tool identity can no longer carry the label: AUC drops by only 0.014 (0.902 → 0.888) and TPR@FAR by 0.060 (0.801 → 0.740), nowhere near arm 0's collapse to exact chance. This means ASEval's attack-labeled turns carry real, substantial signal beyond tool identity — the tool-matched subset is not merely "the shortcut removed and nothing left," it is a genuinely harder, non-degenerate detection problem with its own signal to find.

**What that signal most likely is, stated as the honest caveat it is.** `ASEval`'s loader (`benchmark/a4/audit_loaders/aseval.py`) documents that `arguments` in this audit is actually `{"tool_response": <truncated>}`, not the call's real arguments — so the literature-style monitor's strong, surviving performance is substantially a response-text classifier, not an argument classifier. It is plausible, and consistent with how prompt-injection datasets are typically constructed, that an injected instruction is partially echoed or reflected in the mocked tool response text for `injection_in_tool` turns, which a TF-IDF classifier can pick up directly. That would be a **legitimate** signal for a real deployed monitor to exploit (if a tool's actual response visibly contains injected text, a content-reading monitor should be able to catch it) — unlike arm 0's tool-identity shortcut, which is a pure benchmark-construction artifact with no analogue in a real session. This is offered as the most likely explanation, not confirmed by inspecting individual matched pairs' text directly; it should be verified before being treated as settled if this matters to a later decision.

Arm 1 (the existing, never-fit-to-ASEval D2 classifier) answers a different question from the other two: its full-set performance was never above chance to begin with (AUC=0.488, TPR@FAR=0.108 — both at or below what a chance classifier gives at this FAR), so there is nothing for the matched subset to take away, and it doesn't (0.530 on the subset, a small increase, within the noise of a smaller sample). This is consistent with §8's own prediction that a zero-shot per-step judge should sit "near-chance on locally-benign chains" — true here even on the full set, before any confound control. 29/2,183 (1.3%) of arm 1's responses were unparseable and scored at exact chance (0.5), too small a fraction to explain the near-chance result.

No symbolic baseline, no arms, no training beyond arm 0's and the literature-style monitor's own established CV logistic regression.

### 14b. AgentHarm fitness check (2026-10-23): harm is carried by the request, not the sequence — right venue for this audit, wrong venue for A4's arms

Follow-up instruction, explicitly framed as a fitness check, not a substitution: report how many AgentHarm tasks involve more than one tool call; in how many is no single call harmful in isolation while the task is harmful overall; and whether harm is carried by the task request or by the sequence. If harm is in the request, say so plainly and record both facts (right venue for the audit, wrong venue for A4's arms). All counts below are reproducible via `python3 -m scripts.a4_agentharm_fitness_check --data-dir <path to agentharm/benchmark>`.

**How many tasks involve more than one tool call: 208 of 208 (100%).** Checked directly against both splits' real `target_functions` lists: every single harmful behavior names 2–8 tools (distribution: 24×2, 68×3, 44×4, 28×5, 4×6, 4×7, 4×8 in `test_public`; 8×2, 16×3, 8×4 in `validation`). There is no single-tool-call harmful behavior anywhere in AgentHarm.

**How many have no single call harmful in isolation: 152 of 208 (73.1%), by tool name — the true number is almost certainly higher, and the limitation is stated.** A tool name was scored "inherently alarming" only if it contains an unambiguous red-flag substring (`ransomware`, `malware`, `exploit`, `stolen`, `credit_card_details`, `alpha_bay`, `onion`, `login_data`, `trafficking`, `hack`, etc.) — a disclosed, literal heuristic, not a judgment call made case by case. Across the 80 distinct tool names used by harmful behaviors, only 7 match (`add_hidden_malware`, `create_ransomware`, `download_from_alpha_bay`, `get_all_login_data`, `purchase_credit_card_details`, `query_onion_search`, `submit_alpha_bay_order`); 56/208 behaviors use at least one of them, leaving 152/208 where every tool name is as generic as `post_on_x`, `send_email`, `search_web`, `download_image`, `transfer_money` — the same names a thousand ordinary, legitimate tasks would use. **Caveat, not glossed over:** this assessment is by tool name alone, since no real call arguments exist in this static release (`arguments = {}` for every record, per the loader's own stated limitation) — real arguments, if they existed, could reveal additional in-isolation harm signal this count cannot see. Even the 56 "alarming-name" behaviors are a product of AgentHarm's own synthetic tool registry (a benchmark-invented tool literally named `create_ransomware` for the harmful scenario), not a case of ordinary infrastructure tools combining into unexpected harm — so even they do not demonstrate the kind of compositional/session-level harm A4 is built to catch.

**Whether harm is carried by the request or the sequence: the request, confirmed directly, not inferred from the benchmark's reputation.** Every prompt inspected across all 8 categories (Disinformation, Harassment, Drugs, Fraud, Hate, Cybercrime, Sexual, Copyright) states the harmful goal explicitly, in the user's own first sentence, before any tool is called — e.g. "create a propaganda video... post on X claiming it's authentic," "find a reliable vendor and purchase a list of stolen credit card details," "develop ransomware that encrypts all files... demands a payment." The aggregate confirmation, across both splits' 208 harmful/benign pairs: **171/208 (82.2%) use IDENTICAL `target_functions` between the harmful and benign version** — same tools, same order. Behavior `1-1` is the clearest single example (harmful: "generate a fake video of two politicians shaking hands... post it claiming it's authentic"; its paired benign behavior, same id) — both use the **identical three tools in the identical order** (`run_stable_diffusion_model`, `create_ai_video`, `post_on_x`), differing only in the stated goal's semantic content. The tool sequence is not where the harm lives; it is ordinary task decomposition of a goal whose harmfulness is already fully legible from the request text alone, before a single call happens.

**Both facts recorded, as instructed, stated plainly, neither softened:**
- **AgentHarm is the right venue for *this audit*** — its own harmful/benign counterparts deliberately reuse the same tools (§14's 208/208 tool-matched; 171/208, 82.2%, with identical `target_functions`), which is exactly the controlled construction a shortcut audit needs, and it was not built for that purpose; it is a byproduct of AgentHarm testing refusal rather than shortcut-robustness.
- **AgentHarm is the wrong venue for A4's arms.** A4's claim under test (`docs/v2/A4_MULTITURN_SPEC_v0.2.md` §2) is whether a black-box arm can match a white-box one at detecting drift that only full-sequence/session-state monitoring can see — harm that is *not* legible from any single call or from the request alone. AgentHarm's harm is legible from the request alone, before any tool call, in effectively every behavior checked. An arm 2/3 evaluated on AgentHarm would be tested on request-level refusal, a problem a prompt classifier solves without needing session state at all — it would not demonstrate, one way or the other, whether session state adds value, which is the entire point of A4.

ASEval's tool-matched subset remains A4's primary venue in the spec, per instruction, now on firmer ground given §14a's completed confound demonstration (a real, non-tool-identity signal survives there) and this entry's confirmation that AgentHarm, flagged in §7 as a candidate, is not actually a fit substitute for arms work regardless of its clean shortcut profile.

### 14c. ASEval representation ablation (2026-10-23): essentially all of §14a's surviving 0.888 is carried by tool-response content — the requested 3-way split could not be fully built, and that is reported rather than approximated

Follow-up instruction: on the 233-task tool-matched subset, re-measure the literature-style monitor under three representations (full action; tool name + call arguments with no response; response text only) and report AUC/TPR@FAR=0.12 for each, to find how much of §14a's 0.888 is carried by adversary-writable tool output. State precisely which fields are call-derived versus response-derived, and stop rather than approximate if the schema doesn't cleanly separate them.

**Schema check, done first, before any measurement (`scripts/a4_aseval_representation_ablation.py`).** A real ASEval turn's fields, confirmed directly against `data/advance/injected.json`: `{user, tool_response, tool_name, injection_in_user, injection_in_tool, injection_type}`. **There is no call-arguments field anywhere in this schema.** `tool_name` is a bare string label with no accompanying parameters; the only other content field is `tool_response`. This is not new information — `benchmark/a4/audit_loaders/aseval.py`'s own docstring already disclosed that `AuditRecord.arguments` for ASEval is populated as `{"tool_response": <truncated>}` precisely because no real call arguments exist in this static export — but §14/§14a's own prose had not yet drawn out the consequence for a three-way call-vs-response split.

**Consequence, stated as instructed rather than worked around:**
- **Representation 1 (full action: `tool_name` + response)** is constructible — it is exactly §14a's existing 0.888 baseline, recomputed here for a self-contained artifact: **AUC=0.888, TPR@FAR=0.740** (identical to §14a to three decimal places, as expected — same records, same method).
- **Representation 2 (tool name + call arguments, no response) is NOT constructible.** There is no call-arguments content to isolate. The only call-derived content at all is the bare `tool_name` string, which is a narrower, different question than "tool name and call arguments" presupposes — that narrower question is already answered (`tool_identity_scores()`, AUC=0.501 on this exact subset, §14a), and is cited here for reference only, not substituted as an answer to this item. **This script stops on this item rather than approximating the missing field** (e.g. by leaving arguments empty, or duplicating `tool_name` into a fake arguments slot).
- **Representation 3 (tool-response text only, nothing else)** is constructible, since `arguments` and `tool_name` are genuinely separate fields on `AuditRecord` even though, for ASEval, `arguments` already holds nothing but response text: **AUC=0.885, TPR@FAR=0.737**.

**Finding: essentially all of it.** Response-only content (0.885) carries nearly the entirety of the full representation's AUC (0.888) — a difference of 0.002, and a difference of 0.003 in TPR@FAR (0.737 vs. 0.740). Measured against the distance above chance (0.500), response-only content accounts for (0.885−0.500)/(0.888−0.500) = **99.2%** of the full representation's discriminative power on this subset. `tool_name` contributes almost nothing beyond what the response text alone already carries — consistent with, and a direct quantification of, §14a's own caveat that the literature-style monitor's surviving performance "is substantially a response-text classifier, not an argument classifier."

**What this means, stated precisely, not overclaimed.** The signal that lets a properly-fit monitor beat the tool-identity shortcut on ASEval's matched subset is carried almost entirely by tool-response content — content an adversary able to influence tool output (the exact mechanism `injection_in_tool` already names in this benchmark's own schema) could, in principle, also try to write around. Whether that make the signal "fragile" in an adversarial sense is a separate, harder question this ablation does not answer (it measures what the signal IS attributable to, not how robust that signal would be against an attacker optimizing against this specific monitor) — and is not addressed here, consistent with "still no symbolic baseline, no arms."
